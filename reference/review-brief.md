# 審查 brief 範本（非作者審查員）

審查員用 xhigh，在唯讀的獨立 worktree 裡審。每個軸各派一位：spec 軸看有沒有照規格做，standards／safety 軸看寫法、資料和安全。

```markdown
# 審查：<PR 或 commit>，軸：<spec | standards | safety | security>

## 範圍
- 審查的 head：<完整 SHA>；base：<完整 SHA>
- 規格：<檔案:行號／D-xx>；改動摘要：<一段話>

## 判定規則（一定要照做）
- **只有 P0/P1 才能判「要改」。** P0/P1 的定義：
  - 一般使用就會壞；
  - 存檔資料會遺失，或被悄悄改掉；
  - 資料外洩，或安全性變弱；
  - 主要需求沒做到。
- 其他都是 P2/P3：少見的邊角、修飾、加固、風格。列出來就好，不擋合併。
- 先用一般使用者會打的內容試，再看邊角。
- 每個發現都要附 `file:line` 和失敗情境：輸入什麼，得到什麼錯的結果。

## 必查（BLOCKER）
- 有沒有改到既有測試的邏輯？有的話要列出來，那需要 owner 本人放行。
- 測試有沒有讀固定 commit（git archive／show 某個 SHA）？CI 是淺 clone，會壞。
- 寫死在測試裡的數值變了，主控有沒有先核准？
- 有沒有把金鑰、本機路徑、私有名稱寫進 repo？
- 新模組有沒有登記進每個靜態閘門和打包清單？
- 動到共用的讀取函式時，每個呼叫它的地方都有判定嗎？

## 輸出（審查是唯讀的，不能寫檔：結論就是你的最後一則訊息）
- 第一行：審查範圍 `<base SHA>..<head SHA>`；
- 中間：發現的問題，依嚴重度排列，每個都附 file:line 和失敗情境；P2/P3 另列「之後再修」；
- **最後一行固定格式**，只能是其中一個：`VERDICT: PASS` 或 `VERDICT: BLOCK`（有 P0/P1 才 BLOCK）。
```

派工時用 `-o last.md` 收下最後一則訊息；主控用 `grep '^VERDICT:' last.md` 判讀。要產出檔案的工作（報告、腳本）必須用 worker 模式，審查模式寫不了檔。

**修正後的確認**：只請原審查員看修正的 diff，確認點名的問題修好、旁邊沒有壞掉。不要重新全面審。設計或範圍變了才重審。
