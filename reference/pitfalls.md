# 踩過的坑

## Shell 和工具
- 管線的 exit code 來自最後一個指令：`cmd | tail` 拿到的是 tail 的。要用 `set -o pipefail`，或者 `cmd > out 2>&1; rc=$?`。
- **雙引號裡的反引號和 `$()` 會被執行。** 曾經在寫日誌時，把一段要寫進去的指令真的跑了。只要文字裡可能有反引號，就用 `<<'EOF'` 或 `--stdin`。
- zsh 沒加引號的 heredoc，裡面的反引號也會被執行（吃掉了審查 prompt 裡的兩個名稱）。
- zsh 的 `$VAR:c`、`$VAR:h` 是修飾子：`$T:core/x` 會變成別的東西，要寫成 `${T}:core/x`。開頭是 `=` 的參數要加引號，連 `echo ===` 也會失敗（equals 展開）。
- `pgrep -f` 會比對到自己所在的 shell，寫成 `patter[n]` 可以避開。
- 不要改正在背景執行中的 bash 腳本：bash 是邊跑邊讀檔，跑到一半那次會讀到錯位的內容。
- 背景工作不要在指令裡用 `&`，要用工具本身的背景執行。

## 派工和等待
- 等待腳本給了絕對路徑，會默默等到天荒地老（晚了 3.5 小時才發現 worker 早就做完）。
- 新的 dispatch 資料夾要先確認不存在：寫 `prompt.md` 會直接覆蓋舊的。
- 新的 worktree 沒有裝相依套件，驗收會失敗在 import。用 `[ -d node_modules ]` 檢查。
- 從開過 fast／priority 的對話 resume，會把 fast 帶回來。
- 審查模式是唯讀的，寫不了檔：審查員被要求「寫 verdict.md」時會默默寫不出來，曾因此兩次丟失審查結果。要產出檔案的工作用 worker 模式，審查結論用最後一則訊息。
- worktree 裡的 `node_modules` 可能是連到共用安裝的連結：刪之前先 `ls -ld`，刪了會讓所有 worktree 一起壞。

## 審查和測試
- 審查 prompt 沒寫「只有 P0/P1 擋」：審查判「要改」14 次，只有 1 次是真的 P1，兩包各來回 3 輪。
- 用手挑測試清單：兩次第一輪 CI 紅燈，都出在沒人想到的檔案上，每次損失約 1 小時的 CI 加一輪修正。清單一定要從改動推導出來。
- 審查或 worker 為了自己方便，改了既有測試的邏輯（加斷言、過濾掉新欄位）：這需要 owner 本人放行。改用新功能預設關閉，舊測試就能一個字都不動。
- 對外輸出加了一個新欄位，對方「封閉的驗證器」整個丟掉，而且不報錯。要先讀對方的驗證器，照它的格式寫，再加一個逐字比對的測試。
- 「這是測試專用的接口」照樣會被別人拿去用。改之前先在對方的程式碼裡搜尋，包括用字串取屬性的寫法。
- 測試讀固定的 commit，在 CI 的淺 clone 裡會失敗。

## 量測和上線
- npm 發佈後，新版本可能有約 5 分鐘查不到（404）。等 10 分鐘再判定「沒發出去」。
- `gh release --latest=false` 不可靠，要用 API 設 `make_latest=false`，再確認一次。
- 壓力測試的 stub 一次操作只要 2–5 秒，正式環境要 18–22 秒，結果正式環境 6 分鐘就回滾。單次操作成本對不上，測試結果就不能用來決定正式環境的開關。
- 「全部都過了」常常只是受影響清單過了。要寫「N 個／共 M 個」。
- 數字轉抄錯誤：「26 個 namespace」被寫成「26 張卡」。每個數字都要附出處。

## 協作
- 轉述的決定會出錯：曾經把「Codex 不要開 fast」轉述成「不要用 Codex」。要以 owner 本人說的為準，不能以轉述到達的時間為準。
- 主控沒回覆，不代表同意。
- 規則有兩種讀法時，先跟 owner 確認讀法和目的，再轉給大家。
- 跟 owner 報告時用內部代號，owner 看不懂。要用 tmux 標籤叫人。
- `AskUserQuestion` 會卡住整個工作階段：發問前，先把能平行的工作派出去。或者乾脆改用 desk 問，不會卡住。

## 資料和安全
- 模型供應商的安全過濾擋下時：停下來回報，不要改寫、拆開或換路徑重送。
- 公開 repo 不能出現本機路徑、金鑰、私有名稱、正式環境的精確數字。歷史裡有這些的分支，要先壓成乾淨的 commit 再推。
- 秘密掃描只回報數量和是／否，不印出那一行。家目錄底下，有的檔名本身就是金鑰。
- SQLite：在持有連線的行程裡，對資料庫檔案開、關原生 fd，會釋放整個行程的鎖。這類檔案操作只能放到子程序。
- SQLite 查詢計畫：EXPLAIN 時每個 join 的表都要有資料（沒有統計值時 planner 會選錯計畫）。node:sqlite 的 `LIMIT ?` 每次都會重新 prepare，要寫成 `LIMIT CAST(? AS INTEGER)`。
